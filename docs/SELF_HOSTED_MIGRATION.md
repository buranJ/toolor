# TOOLOR: подготовка переноса на компьютер компании

Подготовлено 2026-10-13. Переключение запланировано пользователем на следующий
день; сегодня действующий сайт, NS, бот и реальные заявки **не переключались**.
Это инструкция оператору, не заявление о готовности Windows-сервера.

## Что подтверждено и что ещё нужно проверить

- Домен зарегистрирован в GoDaddy. Действующие NS: `clint.ns.cloudflare.com`
  и `ruth.ns.cloudflare.com`; старый аккаунт Cloudflare недоступен.
- В текущем аккаунте создана новая зона Free, подготовлены 11 записей сайта и
  GoDaddy-почты. Она не должна обслуживать домен до отдельной смены NS.
- Origin Netlify проверен в кабинете: `toolor.netlify.app`; основной домен
  `toolor.store`, `www` перенаправляется на основной. HTTPS на Netlify включён.
- Корпоративная почта GoDaddy Professional Email / Titan. Значения MX, SPF,
  DMARC, двух DKIM, SRV и `email` сверены с кабинетом провайдера; файл
  `deploy/cloudflare/toolor.store.zone` содержит их. DKIM отсутствовал в старой
  зоне: подготовка новой записи не исправляет действующую почту до смены NS.
- 2026-10-13 публичные запросы DS/CAA не вернули записей. Перед сменой NS
  ещё раз проверить DNSSEC/DS непосредственно у регистратора.
- Полного экспорта старой зоны нет. Выяснить, нет ли других сервисов/поддоменов,
  записей проверки домена, редиректов и правил Cloudflare. DNS quick scan не
  заменяет полный экспорт. Публичные IP Cloudflare НЕ являются origin сайта.
- Ранее через AnyDesk увиден Windows Server 2022 и установлен отдельный
  переносимый Node 24.21.0 без изменения глобального Node 20 и приложений 1С.
  Завершение установки зависимостей, сборка, ACL, службы и перезагрузка
  на том компьютере пока не проверены. Сегодня AnyDesk не подключён.

- `scripts/start-self-hosted.mjs`: production-запуск Next на loopback, приватный
  env, SQLite и проверка перед стартом. `--check` не запускает сервер/запросы.
- `deploy/windows/ToolorWeb.xml`: шаблон службы WinSW 2.12.0, LocalService,
  автоматический старт и перезапуск при аварийном завершении, ограниченные логи.
- `deploy/windows/production.env.example`: пустые серверные ключи, SQLite,
  заявки изначально приостановлены. Заполненный файл хранить только приватно.
- `deploy/windows/Backup-ToolorOrders.ps1`: эксклюзивный JSON-архив и его проверка;
  расписание ещё не установлено, копии не удаляются автоматически.
- `deploy/cloudflare/tunnel-config.example.yml`: только два hostname сайта,
  origin `127.0.0.1:3100`, fallback 404. UUID/credentials появятся при настройке.
- `pnpm orders:storage`: проверка, экспорт Netlify, импорт и резервное копирование.
  Архивы содержат персональные данные: не загружать в Git, публичные каталоги,
  чат, общедоступные облачные папки или диагностические отчёты.

## Этап 1: перепривязка Cloudflare, сайт пока остаётся на Netlify

1. Сверить все 11 записей новой зоны с файлом. Пока ВСЕ записи DNS-only,
   веб-записи `@` и `www` указывают на `toolor.netlify.app`, а не на туннель.
2. Новые NS из **этой** зоны, проверенные в кабинете 2026-10-13:
   `celine.ns.cloudflare.com` и `garret.ns.cloudflare.com`. Повторно сверить
   перед переключением; сегодня в GoDaddy они не внесены.
   Проверить DS/DNSSEC и требования Cloudflare перед подтверждённой сменой NS.
3. Только после отдельного подтверждения изменить NS в GoDaddy. Домен остаётся
   у GoDaddy — это не перенос регистратора. Не удалять старую зону/Netlify.
4. Дождаться активации новой зоны, проверить публичные ответы через независимые
   резолверы, HTTPS `toolor.store`/`www`, `/ru`, `/en`, `/ky`, покупку и бот.
5. Проверить отправку и получение корпоративной почты с владельцем ящика,
   MX/SPF/DMARC/DKIM/SRV. Не включать Email Routing и не проксировать mail/DKIM.
   При проблеме остановиться до переноса сайта. Дождаться обновления DNS-кэшей;
   нельзя обещать завершение всего переноса за несколько минут.

## Этап 2: подготовка Windows без публичного открытия портов

Стандартный новый каталог, не папка приложений 1С/CRM:

```text
C:\TOOLOR\app                           исходники, зависимости и .next
C:\TOOLOR\runtime\node.exe              проверенный переносимый Node 24
C:\TOOLOR\service\ToolorWeb.exe         официальный WinSW 2.12.0 x64
C:\TOOLOR\service\ToolorWeb.xml         проверенный шаблон службы
C:\ProgramData\TOOLOR\secrets\          production.env и tunnel credentials
C:\ProgramData\TOOLOR\data\orders.sqlite локальная база (не SMB/OneDrive)
C:\ProgramData\TOOLOR\backups\          приватные архивы
C:\ProgramData\TOOLOR\logs\web\         ограниченные логи
```

Не копировать `node_modules`/`.next` с macOS: собрать на Windows с lockfile,
проверить `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`. Использовать
проверенный Node 24 и закреплённый pnpm 11.13.1, не менять глобальный PATH/Node
и настройки 1С. WinSW брать только из официального релиза, проверить бинарник
и применимость на этом Windows до установки службы.

Настроить ACL **только перечисленных каталогов TOOLOR**, по локальным SID, чтобы
не зависеть от языка Windows. Administrators (`S-1-5-32-544`) и SYSTEM
(`S-1-5-18`) — управление; LocalService (`S-1-5-19`) — чтение app/runtime и
production.env, изменение data/logs и `.next/cache`. Каталоги secrets/data/backups
не должны наследовать доступ обычных пользователей. Служба не должна менять
исходники и runtime. XML/bin меняет только администратор. LocalService общий для
других служб Windows, не изолированная учётная запись: проверить политику компании.
Не выполнять широкие `icacls /reset`, не менять права Windows/профилей/1С.

Заполнить приватный env вне checkout. Удалять/перемещать существующие dotenv
файлы только после резервирования и проверки владельцем: runner намеренно
отказывается стартовать при `.env.local`/`.env.production*` в checkout.
Не копировать Netlify API-токен в web-службу. Production BOT_TOKEN ранее попал
в переписку: владелец должен отозвать его и приватно заменить перед реальными
заявками. Новый токен не отправлять в чат. Chat ID = ID основного оператора;
сохранить полный подтверждённый список `TELEGRAM_OPERATOR_IDS`, включая основного.
Каждый сотрудник работает только в своём private chat. Новые уведомления пока
идут основному получателю, остальные открывают общую историю через /orders.
Настройку нового webhook выполнить отдельно
после подтверждения новых HTTPS/ключей; не сбрасывать ожидающие обновления.

Туннель создать только с подтверждением владельца Cloudflare. Сохранить его
credentials/config приватно и настроить автозапуск cloudflared по официальной
инструкции; никаких public/LAN routes к 1С/CRM. Не открывать входящие 80/443/3100
на роутере и firewall. Не отключать сертификаты/Defender. Убедиться в постоянном
интернете, отсутствии сна, доступном диске и согласовать ИБ/резервное питание.
Проверить ingress конфигурацию (`cloudflared tunnel ingress validate`) и здоровье
туннеля до изменения веб-записей; шаблон с placeholder запускать нельзя.

## Этап 3: финальный перенос истории (один активный writer)

Сегодня настоящие заявки не выгружались. Завтра отдельно подтвердить перенос
персональных данных в приватный каталог компании и резервную копию.

1. Сначала опубликовать подготовленный код на Netlify с прежним netlify-driver
   и `ORDER_MAINTENANCE=0`, проверить сайт. Не использовать старый deploy без
   поддержки maintenance для финальной паузы.
2. Согласовать короткое окно без работы сотрудника. Приостановить checkout и
   webhook (`ORDER_MAINTENANCE=1`) на Netlify, применить настройки новой публикацией
   при необходимости. Убедиться HTTP 503, дождаться завершения запросов в полёте.
   Telegram 503 не подтверждает update и позволяет его повторную доставку.
3. Проверить **все** старые публичные входы: основной домен, netlify.app, deploy
   aliases/preview URLs. Не считать старые immutable deploy URLs автоматически
   приостановленными: они могут иметь старый код/env. Согласовать блокировку
   старых функций/входов или отзыв их ключей. Не оставлять две работающие checkout
   версии. Если нельзя подтвердить остановку источника — cutover не выполнять.
4. Доступ Netlify для экспорта владелец выдаёт приватно. Env оператора с
   `NETLIFY_SITE_ID`, `NETLIFY_AUTH_TOKEN`, `ORDER_STORAGE_NAMESPACE` хранить вне
   checkout; ограничить доступ и отозвать временный токен после переноса.
5. Из корня checkout, с Node 24 и pnpm (PowerShell-пример, не команда на сегодня):

```powershell
pnpm orders:storage export-netlify --quiesced --env-file C:\ProgramData\TOOLOR\secrets\migration.env --file C:\ProgramData\TOOLOR\backups\final.orders-backup.json
pnpm orders:storage verify --file C:\ProgramData\TOOLOR\backups\final.orders-backup.json --sha256 HASH_FROM_EXPORT
pnpm orders:storage import-sqlite --offline --env-file C:\ProgramData\TOOLOR\secrets\production.env --file C:\ProgramData\TOOLOR\backups\final.orders-backup.json --sha256 HASH_FROM_EXPORT
```

`--offline` означает **служба остановлена**; флаг сам не останавливает процессы.
`--quiesced` — подтверждение оператором паузы, не автоматический DNS/HTTP барьер.
Двойное чтение источника выявляет изменения, но не заменяет приостановку.
Импорт атомарный, только в пустой namespace, без перезаписи/очистки. При
ненулевом коде выхода остановиться; не повторять с новым UUID и не удалять базу.
CLI выводит только количества и SHA-256, скрывает чувствительные ошибки.

Сохранены оба префикса `references/` и `orders/`, номера, контакты, состав,
статусы, ревизии, history, messageId/asFile и состояния доставки. Reference-only
crash claims сохраняются. `uncertain`/`dispatching` не превращать в `pending`:
миграция не должна повторно послать уже принятую Telegram заявку.

6. Сравнить контрольную сумму, число orders/references/recoveryClaims и статусы
   до/после; проверить восстановление копии **в другую пустую** тестовую базу.
   Запустить runner `--check` с приватным `TOOLOR_ENV_FILE`, затем службу в паузе.
7. Проверить localhost, перезапуск службы, аварийное восстановление, затем
   перезагрузку Windows без входа пользователя — только с разрешением компании,
   так как на машине есть 1С/CRM. Проверить службу и туннель после загрузки.
8. Проверить готовность edge-сертификата в новой зоне Cloudflare: сертификаты
   старого аккаунта автоматически не переносятся. Только после этого заменить
   **веб** CNAME `@` и `www` на фактический tunnel
   hostname, проксирование для туннеля включено. Не трогать почтовые записи.
   Проверить HTTPS, адреса языков, image optimizer и hero ассеты/Range.
9. После исчезновения split-brain открыть заявки на новом сервере
   (`ORDER_MAINTENANCE=0`, перезапуск), Netlify остаётся без приёма заявок.
   Одна явно помеченная синтетическая заявка, её получение, «в работу»,
   «отправлен», история, ограничения чужого аккаунта — с подтверждением сотрудника.
   Тест почты повторить после переключения. Не отправлять реальные посылки.

## Резервные копии и откат

Сначала проверить `Backup-ToolorOrders.ps1` и восстановление на Windows.
Затем согласовать ежедневную Scheduled Task до входа пользователя и безопасную
внешнюю копию: диск этого же ПК не защищает от его поломки. Мониторить свободное
место и ошибки службы/backup. Срок хранения/удаление пока не утверждены;
автоматического удаления в скрипте нет. Не копировать работающий `.sqlite`
без WAL/согласованного snapshot; CLI делает согласованный JSON snapshot.

До приёма новых заявок на Windows можно вернуть только веб-CNAME на
`toolor.netlify.app` и восстановить единственный netlify-writer после проверки,
не меняя mail. Если уже появились новые заявки/статусы на Windows, простой
возврат DNS **теряет/разделяет историю**: сначала пауза обоих серверов, backup и
согласованная сверка/обратный перенос. Автоматический обратный импорт в Netlify
не реализован. Не обещать безусловный мгновенный откат. Старые NS возвращать
только если зона там остаётся доступной/корректной; DNS-кэши переключаются не сразу.

## Проверки подготовки 2026-10-13

- `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm build`: успешны.
- 116 unit/integration tests; 130 браузерных проверок успешны в Chromium,
  WebKit и Firefox. Два Chromium-only теста throttling штатно пропущены
  в других движках. Проверены checkout, локализация, каталог и hero.
- Отдельный production-server на `127.0.0.1:3113` с синтетическими ключами
  открыл SQLite через собранный webhook route. Пустой update не отправлял
  Telegram сообщений. Реальные заявки/ключи в эти тесты не подставлялись.
- Проверены межпроцессные CAS, восстановление workflow/receipts, полный откат
  транзакции при ошибке импорта, checksum, запрет перезаписи backup, private
  path и preflight. XML службы синтаксически валиден, PowerShell/WinSW и reboot
  пока не проверены на Windows. Это обязательные проверки завтра.
- Публичный `https://toolor.store/ru` возвращает HTTP 200; действуют старые
  NS clint/ruth. Подготовленные изменения кода не опубликованы/не запушены.
